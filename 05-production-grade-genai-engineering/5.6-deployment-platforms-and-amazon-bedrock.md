# Deployment Platforms and Amazon Bedrock

*Choose between direct provider APIs and managed cloud access based on identity, networking, operations, and feature needs.*

<ReadingTime minutes={5} />

The same model family may be available through a direct provider API and through a managed cloud platform. The architecture decision is broader than endpoint syntax: it includes identity, networking, procurement, regional controls, observability, feature availability, and operational ownership.

## Direct API vs. Managed Platform

| Consideration | Direct provider API | Managed cloud platform |
|---------------|---------------------|----------------------|
| Identity and billing | Provider account and keys | Cloud IAM, accounts, and consolidated billing |
| Networking | Public provider endpoint with application controls | Cloud-native networking options and private connectivity where supported |
| Feature timing | Provider features may appear first | Model and feature support can differ by platform and region |
| Operations | Provider-specific telemetry and limits | Integration with cloud logging, audit, and governance services |

## Amazon Bedrock in the Architecture

Amazon Bedrock is a managed service for accessing foundation models. For Claude workloads, applications can use Bedrock-supported inference APIs while controlling access through AWS IAM. Bedrock also provides platform capabilities such as model invocation logging, evaluation features, prompt caching for supported models, and integration with AWS networking and audit services.

Do not assume every Claude feature, model, region, or parameter is identical across Anthropic's API and Bedrock. Isolate platform differences in the runtime adapter and verify current support before release.

<Callout type="tip" label="Selection rule">
Choose the deployment path that best fits the organization's security and operating model, then confirm it supports the model capabilities the product actually requires.
</Callout>
